### Added
- Settings → Profile, как в Linear (#368; снято с живого Linear 2026-10-09). Одна карточка: Profile picture, Email, Full name, Title («Your job title or role», плейсхолдер «Software engineer», до 128 символов — новое поле `users.title`, миграция `0035_user_title`) и Username («One word, like a nickname or first name», до 40 символов, только буквы, цифры, `-` `_` `.`; его можно менять, он же логин). Поля сохраняются по уходу фокуса или Enter, без подтверждения; отказ — тост «Unable to update profile» с причиной, а введённое остаётся в поле; пустое имя — «Your full name cannot be empty.»; Escape возвращает сохранённое. Аватар 32px затемняется под курсором: без фото клик загружает его («Upload an avatar»), с фото открывается меню Change avatar / Remove avatar, удаление сразу, без подтверждения. У неактивной Leave workspace подсказка «Workspace requires at least one owner». Страница получила адрес `/settings/account/profile`, как у Linear. На телефоне каждая строка — подпись над полем на всю ширину. Отличия от Linear: SVG-аватары не принимаются (только PNG, JPEG, WebP). Проверка — `scripts/profile-browser.mjs`.
- Settings → Administration, как в Linear (первая часть #369; снято с живого Linear и из его кода 2026-10-09). Группа в сайдбаре настроек, «Open settings…», Ctrl/Cmd+K и поиске по настройкам: Workspace, Teams, Members — в порядке Linear, с иконками Linear. Видят её только owner и admin: у buyer и viewer нет ни группы, ни пункта «Invite and manage members» в меню workspace, а адреса `/settings/workspace|teams|members` открывают Preferences. Workspace (`/settings/workspace`): Logo (загрузка PNG/JPEG/WebP по клику, «Recommended size is 256x256px»), Name (сохраняется при уходе с поля, «Workspace name updated»; пустое имя возвращается с «Workspace name can’t be empty»), URL (поле только для чтения с префиксом адреса; клик открывает «Change workspace URL» → Update, затем страница сама переезжает на новый адрес). Старые ссылки, в отличие от Linear, не перенаправляются — об этом сказано в окне. Danger zone → Delete workspace: окно «Verify workspace deletion request», как у Linear, но вместо кода из письма нужно ввести название workspace и отметить «I acknowledge…»; удаляет сразу. Удалить может только owner и не последний свой workspace — иначе кнопка выключена с причиной. Time & region и Member onboarding не перенесены. Teams (`/settings/teams`): пока только вид Linear без Export CSV — «Filter by name…», фильтр Active, Create team (выключена, «Teams are coming soon»), таблица Name / Visibility / Members / Accounts / Created с пустым состоянием; настоящие команды — #371. API: `PATCH /api/workspaces/{id}` принимает `slug` (нормализуется как при создании; занятый — 409 «That workspace URL is already taken»). Проверка — `scripts/workspace-settings-browser.mjs` (1440 и 390px, owner, admin, buyer) и `tests/test_workspaces.py`.
- Зависший worker больше не остаётся незамеченным (#199). Раньше heartbeat и readiness оставались зелёными, а `overall_status` — healthy, когда monitoring cycle застревал на await: аудит видел lag 432 с при «healthy». Теперь API (отдельно от worker) раз в минуту проверяет возраст последнего завершённого цикла: с 360 с в каждый workspace с активным кабинетом приходит срочное уведомление Inbox «Rules are not being checked», после восстановления — «Rules are being checked again»; пока worker стоит, письма и Telegram по Inbox отправляет сам API. Новый публичный `GET /health/worker` отдаёт 503 при зависании (для внешнего uptime-монитора), `/api/health/overview` показывает `worker_cycle_status` и учитывает его в `overall_status`. Ручной workflow «Ops drill (manual)» запускает на сервере учения: восстановление локальной или облачной копии во временную БД/контейнер (теперь и с количествами строк), восстановление uploads во временный volume и учение с паузой worker. Ни одно учение не запускается автоматически.
- Город у сессий в Settings → Security & access, как в Linear (#301): «Helsinki, 18, FI · Last seen about 14 hours ago», у этого браузера «● Current session · Helsinki, 18, FI», в деталях сессии строка Last location; строка переносится только между частями. Место берётся из заголовков Cloudflare `cf-ipcity`, `cf-region-code`, `cf-ipcountry`, хранится у сессии (`web_sessions.location`, миграция `0034`), обновляется вместе с «Last seen» и отдаётся в `GET /api/auth/sessions` полем `location`. Без Cloudflare места нет и строка остаётся прежней. Сайт уже стоит за Cloudflare, поэтому API раньше записывал у сессий и считал rate limit по адресу узла Cloudflare: теперь адрес браузера берётся из `CF-Connecting-IP`. И адрес, и место принимаются, только когда соединение действительно пришло из сетей Cloudflare (`CLOUDFLARE_IP_CIDRS`, по умолчанию опубликованный список); поддельные заголовки при прямом обращении к серверу не учитываются. Город появится после того, как владелец включит в Cloudflare «Add visitor location headers» — шаги в `docs/DEPLOYMENT.md`, раздел «Cloudflare».
- Вход в несколько аккаунтов сразу, как в Linear (#231). Switch workspace → Account → «Add an account…» открывает `/auth/add-account`: тот же вход по почте или паролю с «Back to Buyerly» и «Logged in as <почта>», а первый аккаунт остаётся. Подменю Switch workspace и палитра O then W показывают блок на каждый аккаунт под его почтой, номера идут сквозь все блоки, галочка у открытого; workspace другого аккаунта открывается сразу, без входа, с его данными и правами, а поздний ответ прежнего аккаунта на экран не попадает. Log out и Alt+Shift+Q выходят только из открытого аккаунта и открывают workspace оставшегося, последний — экран входа. Сервер хранит отдельную сессию и CSRF-токен на аккаунт (cookie `buyerly_session_<N>` / `buyerly_csrf_<N>` рядом с прежними, до 5 аккаунтов), запрос называет аккаунт заголовком `X-Buyerly-Account` и никогда не получает сессию другого аккаунта вместо вышедшего; новый `GET /api/auth/accounts` перечисляет вошедшие аккаунты. Без заголовка, как раньше, действует последний вход. На странице приглашения `/invite/<token>` в меню «Logged in as» вернулся пункт «Add an account»: вход в ещё один аккаунт с этим приглашением, не выходя из открытого, и возврат на приглашение. Проверки: серверные тесты изоляции сессий и `scripts/multi-account-browser.mjs`.
- В Settings → Members у строк участников появились действия (#227). Меню «…» своей строки — «Leave workspace…», как в Linear; то же есть в новом блоке «Workspace access» внизу Profile: строка «Remove yourself from workspace» и кнопка Leave workspace без рамки (сверено с живым Linear: строка 64px, кнопка 32px, 13px). Если владелец в workspace один, как у единственного admin в Linear, кнопка неактивна (подпись 0.5, кнопка 0.6), а у своей строки в Members нет меню. Участник просто подтверждает выход («Leave <workspace>?»), владелец в том же окне сначала выбирает нового владельца («Transfer ownership and leave»); если других участников нет, окно предлагает сначала кого-нибудь пригласить. После выхода приложение открывает другой workspace аккаунта. Owner и admin в меню чужой строки видят «Change role…» (Admin, Buyer или Viewer) и «Remove from workspace…» с подтверждением; строку владельца не меняет никто, строку admin — только владелец, как и проверяет сервер. В Linear вместо удаления «Suspend user…», которого в Buyerly нет. Сценарии проверяет `scripts/members-browser.mjs` на 390 и 1440px.
- В custom filters priority inbox подменю «From» показывает всех, как в Linear (#271): всех участников workspace, все правила workspace и Buyerly, без счётчиков уведомлений. Порядок сверен с живым Linear: там сначала люди, затем агенты (Linear) с меткой «Agent»; у нас сначала люди по имени, затем правила с такой же меткой «Rule» (12px, обводка, радиус 6, 8px после имени), Buyerly последним. Теперь в фильтр можно добавить человека, от которого ещё ничего не приходило. Фильтр From находит действия человека, записанные и по Telegram id, и по id пользователя, а в фильтре Inbox такой человек больше не двоится. API: `GET /api/inbox/senders`.
- Видно, как работают вместе несколько правил на одной кампании, ad set или объявлении (#323). В окне выбора правил одной строки Ads Manager, если к ней относится больше одного включённого правила (своих и на весь кабинет), внизу блок «If they all match»: какое правило подействует первым и каким действием, какое подействует, если первое ждёт повтора (Repeat), какие уступят («Gives way to "Stop": turning off goes first») и что оповещения срабатывают сами. Правила разных уровней разделены («On this campaign», «On each ad set»). Когда правило подействовало, а другие уступили, его запись в Inbox, Telegram и письме заканчивается «Gave way to this rule: "Scale" (raise budget)».
- Видно, почему правило сработало или молчит на конкретной кампании (#322). В списке правил вместо «Last run» две колонки: Last check — последняя проверка, даже если условие не выполнилось (раньше такое правило выглядело как «Never»), и Last action — последнее действие. В меню строки и карточки правила появился пункт «Status on campaigns» (или ad sets / ads — по уровню правила): окно со всеми сущностями, которые правило проверяет, и состоянием на каждой — «Fired» (и когда повторит), «Waiting until 00:00» (Repeat: Once a day), «Confirming stop until …», «Undone for today» (действие отменено в Inbox, запись №46), «Gave way to <правило>» (уступило более сильному действию или правилу с тем же действием, запись №47), «Condition not met» со значениями метрик и порогами («Spend 3.00 USD, needs ≥ 10.00 USD»), «Campaign is not running», «Failed» с ответом Meta. То же со стороны кампании: окно выбора правил одной кампании или ad set в Ads Manager показывает под списком «Status on this campaign» — каждое правило и его состояние. Состояние — снимок последней проверки: worker перезаписывает его каждую проверку в новой таблице `rule_entity_states` (миграция `0033`), в Inbox ожидания и уступки не попадают; решение — запись №48 в `docs/DECISIONS.md`. API: `last_checked_at` у пресета, `GET /api/presets/{preset_id}/states`, `GET /api/rule-states`. Сценарии проверяет `scripts/rule-states-browser.mjs` на 390 и 1440px.
- Правило снова можно привязать к кампании или ad set прямо в Ads Manager, в том числе с телефона (#320). Колонка Rules вернулась на вкладки Campaigns и Ad sets (её можно скрыть в Display options): «N rules» или «+ Rule», и «+ Rule» видна всегда, а не только при наведении. Выбор правила работает как раньше: отметка привязывает, повторная — отвязывает. Как в Meta («выделить кампании → Rules → Apply rule to»), в меню действий над выделенными строками появился пункт «Apply rule…» (клавиша A): одно окно выбора для всех выделенных строк, правило, привязанное только к части из них, отмечено чёрточкой, и нажатие привязывает его ко всем, а следующее — снимает со всех выделенных. На телефоне чекбокс выделения строки виден всегда, строки в окне выбора выше (44px), а клавиатура сама не выезжает. Сценарии проверяет `scripts/rules-attach-browser.mjs` на 390 и 1440px.
- Палитры «Open …», как «Open issue…» в Linear (#312, последняя часть #308). O и буква открывают окно быстрого перехода к записи: O C — кампания, O A — ad set, O D — объявление (A уже занята), O R — правило, O K — рекламный кабинет, O S — страница настроек; O W, как и раньше, — workspace. При вводе поиск идёт сразу: «Quick results for "…"» из `GET /api/search?kind=…`. Если показывать нечего — ничего ещё не открывали или ничего не нашлось — под полем пусто, как у Linear: ни надписи, ни подвала. У правила перед названием приглушённый идентификатор RUL-07, как BUY-4 у Linear. Подвал — кнопки-«таблетки»: ↵ Open слева, Alt ↵ More actions и Quick look → справа. ↵ открывает запись на её строке, как поиск. Alt+↵ (More actions) открывает её строку сразу с меню действий (Pause/Resume delivery, у правила ещё Delete); у рекламного кабинета своей строки нет, и этой кнопки у него тоже. → в конце текста показывает Quick look: окно вырастает до 487px, список сужается до 304px, справа — вид записи (или RUL-07), название 18px, приглушённая строка «статус · возраст» и данные записи; ← его прячет, а Esc, как у Linear, сразу закрывает окно. «Open settings…» перечисляет страницы настроек с их иконками из сайдбара: свои страницы первыми без заголовка, Members — под «Administration», как группирует Linear; подвала нет. В Ctrl/Cmd+K в Navigation появились Open campaign… / ad set… / ad… / rule… / ad account… / settings… с клавишами «O then C» и т. д.
- Меню действий над выделенными строками (Ctrl/Cmd+K при выделении), как у Linear: вместо заголовка группы над полем плашка — одна строка по имени («RUL-07 ⋅ Test stop without leads», кампания — просто названием), несколько — числом («3 campaigns»). ⌫ на плашке или Backspace в пустом поле снимает её и открывает обычное меню команд. Шире 1024px панель — колонка, под которую список отдаёт место: она больше не перекрывает таблицу, тулбар и кнопки шапки. ### Fixed
- Ошибки Meta во время действий правил и Undo (#200), найдены тренажёром `scripts/rule_simulator.py`, который теперь пишет в Meta через настоящий `MetaClient` и поддельный узел с 429, 503, обрывами до и после применения и истёкшим токеном (сценарии и измерения — `docs/PILOT_SIMULATION.md`, закреплены в `tests/test_rule_simulator.py`). **Применённое, но «упавшее» действие:** если запрос оборвался после того, как Meta применила изменение, и повторы не дошли, Inbox сообщал о сбое и Undo был недоступен; теперь worker один раз читает состояние в Meta и записывает успех, если изменение есть (статус и бюджет). **Истёкший токен при записи** сразу даёт TOKEN_EXPIRED, отмечает здоровье кабинета и останавливает остальные действия кабинета в цикле, а не ждёт следующего чтения. **Повтор Undo** после оборванной, но применённой записи больше не отвечает «state already differs»: он признаёт отменённое состояние и записывает Undo без новой записи в Meta.
- Точность метрик на ненулевых данных (#212), найдено «золотым» тестом `tests/test_metrics_golden.py`: поддельный Graph API (MockTransport за настоящим MetaClient) отвечает как Marketing API, настоящий worker синхронизирует кабинеты Pacific/Auckland (UTC+13) и Pacific/Honolulu (UTC−10) в NZD, а каждое число API сверяется со значениями, посчитанными в тесте по определениям Meta. **Полночь кабинета:** синхронизация из ~8 запросов, начатая за секунды до полуночи, записывала первые секунды нового дня под старой датой — Meta разрешает `date_preset=today` в момент каждого запроса. Теперь иерархия запрашивается явным `time_range` локального дня кабинета, а день берётся из часов цикла. **Закрытый день:** worker синхронизировал только `today`, поэтому «Yesterday» и неделя навсегда оставались с итогами последней синхронизации до полуночи, без последних минут расхода и конверсий, которые Meta относит к дню клика. Теперь вчерашний день перечитывается раз в час, пять дней до него — раз в сутки (по одному дню за цикл, только сущности с показами). **Принудительное обновление Summary:** `force=true` за last_3d/last_7d записывал многодневный итог в факт одного дня (к тому же по дате UTC) и запрашивал у Meta пресет, окно которого может отличаться от окна хранилища; теперь запрос идёт теми же локальными днями, а факт пишется только для однодневного периода и по дате кабинета. **Округление:** CPC 26.75 / 10 показывался 2.67 (двоичное `round`), Ads Manager показывает 2.68; деньги и доли округляются половиной вверх, суммы расхода — до целых центов перед делением. **Нет знаменателя:** CTR, CPC и CPM строки без показов или кликов в Ads Manager теперь `null` («—»), а не 0.00.

- У web-сессии записывался адрес прокси (nginx в Docker), а не браузера: теперь адрес берётся с учётом доверенных прокси (`TRUSTED_PROXY_CIDRS`), как в rate limit, и обновляется вместе с «last seen», чтобы список входов показывал, где сессию видели последней.
- Правило на паузе больше не глушит другие правила на той же сущности (#296). Раньше из всех сработавших правил выполнялось одно, и если оно стояло на паузе (Repeat), молчали и остальные: второе оповещение на кампании не приходило, пока было привязано первое. Изменение сущности по-прежнему одно за проверку: побеждает самое сильное действие (остановка, затем уменьшение бюджета, затем увеличение), из правил с ним — первое не на паузе. Пока остановка на паузе, подъём бюджета её не подменяет.

Объявление — лист дерева, суммировать в него нечего, поэтому список объявлений и их метрики по каждому нужному окну читаются отдельно — и только в те циклы, когда правило уровня объявления действительно должно сработать.
- Прицел правила работает и для объявлений: область по кампании выбирает объявление через его кампанию, область по адсету — через его адсет. Кампанию область по адсету не выбирает никогда.

Теперь проверку выполняет код работающего релиза (`python -m database.restore_check` в контейнере API) по этапам с отдельным итогом: архив, версия схемы (revision должна быть из истории миграций релиза; старая известная поднимается до head во временной базе), контракт схемы (таблицы, колонки, семейства типов, внешние ключи моделей), данные (проверенные внешние ключи, есть пользователи и workspace) и чтение через приложение (все модели через ORM, расшифровка Meta-токенов). Раньше `scripts/backup_db.sh` писал дамп сразу в итоговое имя: если `pg_dump`, сжатие или шифрование обрывались, на диске оставался обрезанный `buyerly_postgres_….sql.gz(.enc)`, и `restore_db.sh --latest-local` выбирал именно его как самый новый. Теперь дамп пишется во временный скрытый файл, читается обратно так же, как при восстановлении, проверяется метка конца `pg_dump`, и только потом файл переименовывается. При ошибке файла с настоящим именем нет, время последнего бэкапа не обновляется и в облако ничего не уходит. `restore_db.sh --download-latest-offsite` раньше всегда сохранял скачанное как `.sql.gz.enc` и пытался расшифровать даже незашифрованный архив; теперь файл сохраняет имя объекта из хранилища, а содержимое сверяется с расширением до обращения к базе.
- Бэкапы по расписанию и при деплое теперь видят настройки шифрования и облачного хранилища из `.env` (#197, C06). Раньше `scripts/backup_db.sh` брал `BACKUP_ENCRYPTION_KEY` и `S3_*` только из окружения, а cron и `deploy.sh` запускают его без них: Compose передаёт `.env` контейнерам, не хосту. Даже с заполненным `.env` получался незашифрованный архив, который никуда не выгружался, и лог этого не показывал. Теперь `backup_db.sh` и `restore_db.sh` сами читают эти семь ключей из `.env` как текст, не выполняя файл. Если ключи S3 заполнены, но не хватает адреса, бакета, второго ключа или ключа шифрования, бэкап останавливается с понятной ошибкой вместо тихого локального режима. `backup_db.sh --check-config` показывает режим без значений; `setup_backup_cron.sh` проверяет настройки в пустом окружении перед установкой, передаёт путь к `.env` явно, пишет лог без root в домашний каталог и честно называет время запуска «03:00 по времени сервера», а не UTC.
- Восстановление базы из повреждённого бэкапа больше не портит текущую базу (#205). Раньше `scripts/restore_db.sh` распаковывал архив прямо в PostgreSQL: если файл был обрезан или ключ не подходил, ошибка обнаруживалась в конце, когда старые таблицы уже были удалены и частично перезаписаны. Теперь архив целиком расшифровывается и распаковывается во временный файл рядом с архивом (не в `/tmp`), проверяется метка конца `pg_dump`, и только потом дамп применяется одной транзакцией (`--single-transaction`): ошибка SQL посреди восстановления откатывает всё. Повреждённый gzip, обрезанный зашифрованный архив, неверный ключ, обрезанный дамп и ошибка SQL проверены на PostgreSQL 16.15 — во всех случаях код выхода 1 и прежние данные на месте; исправные `.sql.gz`, `.sql.gz.enc` и `.sql` восстанавливаются. Место для временного файла задаётся `RESTORE_WORK_DIR`.

- Settings больше не показывают ошибки чужих workspace (#203). Раньше worker сохранял тексты последних ошибок цикла в общую запись `monitoring`, и `GET /api/settings` отдавал их любому вошедшему, включая Viewer другого workspace: в тексте мог быть ID чужого рекламного кабинета и `access_token`. ## [1.1.0] - 2026-08-23

### 🔒 Безопасность и отказоустойчивость (Hardening & Security Release)

#### Added
- **Rate Limiting Engine**: Потокобезопасный `RateLimiter` на базе скользящего окна (Sliding Window) с автоматической очисткой устаревших записей памяти и поддержкой заголовков прокси (`X-Forwarded-For`, `X-Real-IP`).
- **Rate Limiting на критических эндпоинтах**:
  - `/api/auth/login` (10 req/min) — защита от подбора паролей.
  - `/api/auth/request-temporary-password` (5 req/min) — защита от флуда одноразовыми паролями.
  - `/api/invites/{token}` и `/api/invites/{token}/accept` (30 и 10 req/min) — защита от перебора инвайтов.
  - `/api/onboarding/check-slug` (30 req/min) — защита от перебора названий воркспейсов.
  - `/api/meta/oauth/start` (10 req/min) — защита от исчерпания сессий OAuth.
  - `/api/accounts/parse-raw` (20 req/min) — защита парсера.
- **OTP Brute-force Protection**: Блокировка одноразовых кодов после 5 неверных попыток (`failed_attempts >= 5`) и 60-секундный кулдаун на повторную отправку.
- **Payload Size Middleware**: Ограничение максимального размера тела запроса (10 МБ для загрузки медиафайлов, 1 МБ для всех остальных API-запросов) с возвратом HTTP 413 `Payload Too Large`.
- **ReDoS Protection**: Ограничение входного текста в `parse_fb_raw_accounts` до 64 КБ / 2000 строк, обрезка названий до 120 символов и лимит вывода до 500 записей.
- **Security Headers**: Автоматическое добавление заголовков `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-XSS-Protection: 1; mode=block`.
- **Docs**: Добавлен подробный итоговый отчет по безопасности `docs/security_audit_report.md` (позже удалён).
- **Automated Tests**: Набор тестов расширен до 197 сценариев, включая проверки скользящего окна, блокировки OTP, валидации инвайтов и изоляции воркспейсов.

#### Fixed
- **Funnel Guard Bypass**: Исправлено поведение правил остановки: защита воронок `funnel_guarded` теперь требует явного минимального порога конверсий (`min_conversions_for_cpa > 0`), исключая обход стопа при нулевых конверсиях.
- **Cross-Workspace Hijack**: Запрещен межворкспейсный захват рекламных кабинетов через `Batch Add` и ручной импорт.
- **Rule Snapshot Isolation**: Предотвращена нежелательная каскадная мутация работающих правил в рекламных кабинетах при изменении пресетов.
- **Session Token Entropy**: Генерация токенов авторизации переведена на криптостойкий генератор `secrets.token_urlsafe(32)` (256 бит энтропии).
- **Targeted Invites**: Приглашения с указанием Email теперь могут быть приняты только пользователем с подтвержденным соответствующим email.
- **SVG Stored XSS**: Запрещена загрузка файлов формата SVG для аватаров и логотипов воркспейсов.
- **CORS Misconfiguration**: Исправлена небезопасная комбинация `allow_credentials=True` при открытом `origins=*`.
